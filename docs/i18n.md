# Localization (Windows client)

The Windows client shows its own chrome — menus, settings, dialogs, toasts —
in the user's language. Web content is Chromium's business and is unaffected.

Shipping locales: `en de es fr ja ko nl pt-BR zh-Hans zh-Hant`. The first
nine are the ones the Mac ships; `pt-BR` (Brazilian Portuguese) is listed
ahead of the Mac catalog carrying it, and arrives through the translation
repository (phibrowser/phi-i18n#2).

The list lives in two places: `LOCALES` in `tools/gen-strings-catalog.py`,
which writes it into `strings.json` as `"locales"`, and the endonym table in
`PhiLocaleDisplayName` (`client/phi_i18n.cc`). The runtime takes its
available locales from the GENERATED catalog, so a locale added to `LOCALES`
shows up in the language picker only once `strings.json` is regenerated, and
only once it carries `MIN_COVERAGE` (90 %) of the keys. Below that the
generator still writes its strings but leaves it out of `"locales"` and says
so, because a listed locale is offered in the picker and picked for a
matching Windows language: an untranslated one would be an English UI under
a Portuguese name. `pt-BR` is held back this way today.

## Where translations come from

**This repository does not own translations.** The product's single source is
the Mac catalog, `phibrowser-mac/Resources/Localizable.xcstrings`, which the
dedicated translation repository maintains. The Windows client joins it:

| File | Owns |
|---|---|
| `client/resources/strings-source.json` | the KEYS this client asks for, their English value, and a translator comment |
| `phibrowser-mac/Resources/Localizable.xcstrings` | the translations |
| `client/resources/strings.json` | the generated catalog that ships beside the exe |

`tools/gen-strings-catalog.py` joins the two. For every key it takes the Mac's
translations **by key** when the Mac carries that key, otherwise **by exact
English match** — which is how wording that was deliberately ported keeps one
translation on both clients. A Windows "Pin" and a Mac "Pin" cannot drift.

Run it after touching the source file, and whenever the Mac catalog is
updated:

```bash
tools/gen-strings-catalog.py            # write the catalog
tools/gen-strings-catalog.py --check    # report coverage, write nothing
```

An untranslated key is reported and falls back to English at runtime, which is
the same degradation the Mac has for a key awaiting the translation repo.

A source entry's own `translations` block replaces the Mac match AS A WHOLE,
not per locale. So a locale added after those blocks were written gets
nothing from the Mac for them, even where the Mac has the string: the key
reads English in that locale until its block gains the locale too. `pt-BR` is
in that position today. The 502 Windows-only blocks carry the original eight
languages only, so a catalog built against a Mac catalog with full `pt-BR`
still leaves those 502 keys in English for Brazilian users.

## Adding a string

1. Add a key to `strings-source.json` with its English value and a comment.
   Keys are `productArea.surface.purpose`, lower-camel-case, the Mac's
   convention. If the Mac already has this exact English, use the Mac's key
   and the translation arrives for free.
2. Call it: `PhiStr("menuBar.newTab")` returns `const wchar_t*`, so it drops
   straight into `AppendMenuW`, `MessageBoxW` and friends.
3. Regenerate the catalog.

### Two rules that are easy to get wrong

**Never concatenate a sentence.** `L"Deleting " + name + L" cannot be undone."`
has no translation — languages reorder clauses. Write one key with positional
placeholders and use `PhiStrF`:

```cpp
PhiStrF("menuBar.tabsBookmarkedToast", {std::to_wstring(added)})
```

The generator rewrites the Mac's printf placeholders (`%d`, `%@`, `%1$@`, …)
to positional `{0}`, `{1}` tokens as it joins, so a key shared with the Mac
formats through `PhiStrF` on Windows without a Windows-only copy of the string.

**Author labels bare.** The Windows `&` mnemonic and the `\tCtrl+N`
accelerator are layout, not language; the generator re-applies them around
whatever translation it finds. The exception is a menu-bar TITLE, whose
mnemonic letter is genuinely language-specific ("&Datei", "文件(&F)"): those
entries set `"verbatim": true` and carry the decoration inside each value.

## Choosing the language

`Settings ▸ General ▸ Display language`. "System default" is the default and
the only choice that follows a later change of the Windows UI language; the
rest are endonyms, so a language is findable without first reading the one the
app happens to be in. The choice persists as `language` in `PhiSettings.json`.

Resolution order: the stored preference, else the OS preferred-UI-language
list, else English. Matching is case-insensitive and script-aware — a Windows
`zh-Hant-TW`, `zh-HK` or `zh-MO` resolves to `zh-Hant`, any other Chinese to
`zh-Hans`, and an unknown region falls back to its bare language subtag.
That last rule covers Portuguese on purpose: a Windows `pt-BR` matches
exactly, and `pt-PT` or a bare `pt` falls back to `pt-BR`, since Brazilian
Portuguese reads closer to a Portuguese user than English does. A `pt-PT`
catalog, if one ever ships, wins by exact match with no code change.

Plurals follow CLDR per locale (`PhiPluralFor` in `client/phi_util.cc`):
`pt-BR`, like `fr`, counts 0 as singular ("0 aba", "1 aba", "2 abas"), while
CLDR gives `pt-PT` the English rule.

Switching rebuilds the chrome: menus cache their strings inside HMENUs and
cannot be repainted, so `PhiWindowController::RebuildMenuBar()` recreates
them and the caption band re-measures its title rects.

## The other half: Chromium's own UI

The client draws most of the browser, but not all of it. Web-content context
menus, error pages, permission bubbles, print preview and the PDF viewer are
Chromium's, and they read a completely separate catalog: the locale packs in
`locales/*.pak`, chosen ONCE at startup from the `intl.app_locale` local-state
pref (`chrome/browser/chrome_resource_bundle_helper.cc`). Switching the
client's catalog alone leaves that half in the system language forever, which
is what it did until this was wired up.

So `PhiCoordinator::PushDisplayLanguageToChromium()` hands the preference to
`PhiFramework::SetDisplayLanguage()`, which

1. writes — or clears — `intl.app_locale`, which is what survives a restart;
2. resolves what that pref will actually load; and
3. reloads the locale pack in the running process, so the switch shows up
   without one.

It runs on every change AND once at startup from `OnFrameworkReady`: the
client reads its prefs in its constructor, before there is a framework to
tell, and a preference file edited while the browser was closed has to be
reconciled somewhere.

Three details that bite:

* **Chinese is named twice.** The catalog uses script tags (`zh-Hans`), the
  locale packs the legacy region ones (`zh-CN`). Chromium's own
  `CheckAndResolveLocale` reads "Hant" as a *region* and lands on Simplified,
  so the framework maps both explicitly. The Mac client makes the same
  translation for its bundle identifiers.
* **"System default" must ask Windows, not ICU.** With an empty pref,
  `l10n_util::GetApplicationLocale` defers to ICU's default locale — which an
  explicit choice earlier in the same process has already moved. Resolving
  that way would hand back the language the user just left, so the framework
  reads `GetUserPreferredUILanguageList` itself.
* **Each half then decides for itself.** Chromium ships around a hundred
  locales, the client ten. On an Italian machine with no preference set, what
  Chromium draws is Italian while the client's chrome falls back to English.
  That is the same split the Mac has, and it beats pinning Chromium down to
  the client's shorter list.

Already-built UI keeps the strings it was built with — the client rebuilds its
menu bar for exactly that reason. Chromium's share is built on demand, so it
comes up in the new language; a chrome:// page already open changes on its
next load, and renderers spawned after the switch receive the new `--lang`.

One thing does lag a live switch: a COMPONENT EXTENSION resolves its
`_locales` messages when it loads, so the Skill recorder's "Record a Skill"
context-menu item keeps the language it started in until the next launch.
Everything around it switches immediately, and the persisted pref means the
extension loads in the right language from then on.

The web content's own languages — `Accept-Language`, `navigator.language` —
are a separate profile preference, untouched by this, exactly as they are in
Chrome.

## Runtime notes

* The catalog is read with plain Win32 file I/O, never `base::ReadFileToString`.
  It loads lazily on the browser UI thread, which disallows blocking calls once
  the message loop is running — the trap `phi_emoji.cc` hit.
* A pointer from `PhiStr` is valid for the life of the process. Per-locale maps
  are never erased; a language switch points at a different map. A menu built
  before a switch stays readable until it is rebuilt.
* Lookup never fails: active locale, then English, then the key itself. A bare
  key on screen is loud enough to spot in a screenshot and cannot crash a menu
  build.

## Status

Converted: the menu bar (titles, every item, and its dialogs), the whole
Settings window (every page, the rail, the search results, its rename /
create / delete prompts and the shortcut recorder in `phi_prompt.cc`), plus
Chromium's own UI, which follows the same choice. Settings reuses the Mac's
keys wherever the English matches (`settings.navigations.*`,
`settings.advanced.*`, `themes.theme.<id>.name`, …), so most of it arrives
translated; its Windows-only wording (`settings.search.*`,
`settings.a11y.*`, the Kiosk Ctrl+Alt rows, the profile "Used by" plurals)
waits for the translation repo and reads English until then.

Two Settings habits worth copying elsewhere:

* **Counts are plural families.** "Used by Work, Home · 2 Spaces" is
  `PhiStrN("settings.profiles.usedByHint", count, {names})` — never
  `to_wstring(n) + L" Spaces"`.
* **An accessible name is a sentence too.** A slider's or drop-down's name
  ("Saturation: 40%", "Color appearance: Dark") goes through
  `settings.a11y.*` format keys, not a concatenation.

Everything else still uses literals and reads English; those strings
already have keys in the source file, so converting a surface is a
mechanical pass, and the translations for roughly half of them are already
in the catalog.
